# Final report — offer-diff

## Implemented scope

Builds exactly the brief in `TASK.md`: upload an original and a revised commercial offer
(PDF), get back the substantive changes (scope/quantities/unit prices/totals/delivery
dates), each referencing both source documents, plus arithmetic-discrepancy detection and
explicit decline-to-conclude behavior when the inputs fall outside the stated scope
(currency mismatch, or over the page/line-item limits).

Explicitly out of scope (per the brief, not attempted): OCR/scanned or handwritten PDFs,
multi-currency comparison, legal analysis, accounts, payments, multi-language input.

## Complete flow

1. Browser: user selects `original.pdf` and `revised.pdf`, clicks Compare.
2. `POST /api/compare` (multipart, two files) — `src/server.ts`.
3. `extractText()` (`src/pdf/extractText.ts`) — deterministic, per-page text extraction via
   `pdfjs-dist`, no OCR.
4. `StructuringProvider.structureOffer()` — turns raw text into a structured
   `{docTitle, currency, offerDate, deliveryDate, items[], printedGrandTotal, ...}` record,
   with a page+verbatim-snippet reference for every field. Real implementation:
   `ClaudeStructuringProvider` (Anthropic tool-use / forced JSON schema, temperature not
   applicable — tool_choice forces structured output). Currently not exercised with a real
   key; see "Known limitations."
5. `matchItems()` (`src/matching/matchItems.ts`) — deterministic, order-independent,
   rename-tolerant (token-Jaccard similarity) matching between original and revised line
   items. Exact / confirmed / uncertain confidence tiers.
6. `computeDiff()` (`src/diff/computeDiff.ts`) — deterministic: currency-mismatch decline
   check, per-matched-pair quantity/price comparison, removed/added items, date comparison
   (format-tolerant), independent recomputation of each document's total from its own line
   items compared against the printed total (arithmetic discrepancy, never silently
   corrected).
7. JSON response rendered by `public/app.js` into a concise, decision-oriented report:
   substantive changes table (with source references), arithmetic discrepancies, uncertain
   matches, or a decline banner.

## Difficult inputs tested

Test set: `test-set/input/{normal, ambiguity-reorder-badtotal, decline-currency-mismatch,
formatting-only}`, generated by `scripts/generateFixtures.ts` (deterministic, ground truth
recorded in each scenario's `ground-truth.json`, expected differences written to
`expected.md` before ever running the pipeline). Full expected-vs-actual comparison:
**`docs/test-report.md`**. Summary: **4/4 pass**.

- **normal**: quantity change, unit price change, item removed, delivery date changed — all
  4 detected, correctly referenced, no false positives.
- **correction/ambiguity** (renamed + reordered item, intentionally wrong printed total):
  item matched across rename+reorder (Jaccard similarity 0.75, correctly surfaced as an
  *uncertain* match rather than asserted with false confidence or split into a false
  removed+added pair); the real quantity change on that item was still correctly attributed
  to it; the wrong printed total was flagged as a 27.50 arithmetic discrepancy rather than
  silently trusted or silently "corrected."
- **clarification/decline** (currency mismatch, USD vs EUR): correctly declined to compare
  amounts instead of guessing.
- **formatting-only** (case, date format, thousands separators changed, nothing else): 0
  substantive changes reported, as required by the brief.

## Usability notes

- Single-screen flow: two file pickers, one button, one report. No accounts, no multi-step
  wizard.
- The report leads with a decline/no-change banner when applicable, so a reviewer sees the
  bottom line first; the full change table is secondary.
- Every change row carries the literal source text it came from (page + snippet) so a human
  can verify a claim against the PDF in seconds, per the brief's "every change must
  reference both source locations" requirement.
- A visible banner explains when the mock parser (not real AI) produced the result, so a
  reviewer is never misled about what actually ran.

## Tradeoffs

- **Decision:** use an LLM only for text-to-structured-JSON extraction, and keep matching,
  diffing, and arithmetic entirely in deterministic code.
  **Reason:** the brief requires "recalculate totals deterministically... do not silently
  replace what the source says" — arithmetic and identity decisions must be auditable and
  reproducible, which an LLM's own arithmetic is not.
  **Alternative considered:** ask the LLM to do the full comparison in one call.
  **Tradeoff:** more total LLM calls (2 structuring calls instead of 1 comparison call), but
  every number and every match decision is independently unit-testable without an API key.

- **Decision:** token-based Jaccard similarity for item matching, not full ML/embedding
  similarity.
  **Reason:** deterministic, dependency-light, testable, and transparent about *why* two
  items matched (shared tokens), which matters for a decision-support report a human must
  trust.
  **Alternative considered:** embedding-based semantic similarity (via an API call).
  **Tradeoff:** would handle synonyms ("Bolt" vs "Fastener") better, at the cost of another
  paid API call per item pair and much harder-to-audit "why did it match" reasoning.

- **Decision:** regex mock fallback when no API key is present, instead of blocking all
  progress on a funded key.
  **Reason:** the user could not immediately fund an Anthropic API key; the brief's other
  80%-weighted criteria (flow, difficult inputs, evidence, usability, reproducibility) do
  not require the AI step specifically to be exercised to be demonstrated.
  **Tradeoff:** the "measured speed/cost" criterion for the AI step specifically is left
  honestly unmet pending a key, rather than fabricated.

## Known limitations

- **The AI structuring step has not been exercised with real API calls.** `ClaudeStructuringProvider`
  is implemented and type-checked but unverified at runtime; its accuracy on the ground-truth
  fixtures (`test-set/input/*/ground-truth.json`) is untested. This is the single largest
  open item.
- The regex mock only understands this project's own fixed table layout; it will silently
  under-extract or fail on real-world offer PDFs with different formatting. It exists only
  for demoing the rest of the pipeline, not as a general solution.
- Date parsing supports ISO (`YYYY-MM-DD`) and one long-form pattern (`Month D, YYYY`) only;
  other real-world date formats will fall back to raw string comparison, which may
  under-detect (miss) formatting-only date changes it doesn't recognize, or over-detect a
  format it can't parse as a "change." Not exercised beyond the two formats in the test set.
- No multi-currency support (by design, per scope) — mismatched currency triggers a decline
  rather than a conversion.
- Not deployed publicly; browser demo is local (`npm run dev`).
- Exact current Anthropic API pricing not confirmed from the primary source (network egress
  restriction in this environment) — see `docs/cost.md`.
